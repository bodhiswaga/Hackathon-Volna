задачи, зависимости, критический путь и **what-if анализ последствий изменений**. Главный вопрос продукта:
«Если сейчас что-то изменится, что произойдёт с проектом и на что мне обратить внимание?»

## Питч и презентация

Раздел для слайдов и устного питча. Цифры проверены на 2026-09-29.

### Одной фразой
**«Волна» показывает, что случится с проектом из-за изменения, до того как вы его примените, и помогает выбрать,
что делать дальше.**
Короче, для слайда: «Измени план — увидь последствия — выбери решение — сообщи заказчику».

### Проблема
- План проекта меняется постоянно: сотрудник уходит в отпуск, задача оказывается сложнее, заказчик меняет требования,
  подрядчик задерживает свою часть (все четыре события названы в ТЗ).
- Руководитель двигает одну дату в календаре, но не видит, что поедет за ней: какие задачи сдвинутся по цепочке,
  сорвётся ли дедлайн, кого из команды это заденет, насколько вообще надёжен план.
- Массовые инструменты показывают диаграмму Ганта без последствий (Битрикс24, YouGile, WEEEK, monday), а what-if
  и вероятностный прогноз есть только в тяжёлых экспертных системах (Primavera, Acumen), рассчитанных на планировщика,
  а не на руководителя.

### Пользователь
Руководитель проекта в небольшой команде (5–30 человек, продуктовая или заказная разработка): отвечает перед заказчиком
за срок, сам ведёт план, отдельного планировщика-аналитика у него нет. Главный вопрос из ТЗ — его вопрос:
**«Если сейчас что-то изменится, что произойдёт с проектом и на что мне нужно обратить внимание?»**

### Решение: полный цикл руководителя
1. **Предвидеть.** «Шанс успеть» — вероятность уложиться в дедлайн (2000 прогонов плана); «Шторм-тест» — какие сбои
   сорвут срок, пока они не случились; запас прочности каждой задачи.
2. **Понять.** Любая правка сначала черновик: оранжевая «волна» сдвигов на таймлайне, прежние даты призраками, причина
   каждого сдвига цепочкой («сдвинулась, потому что ждёт Backend»), вердикт «можно применять / есть последствия /
   требуется вмешательство». «Что случилось?» превращает событие из жизни (отпуск, подрядчик, новое требование) в правки плана.
3. **Решить.** Советник предлагает ускорение, нахлёст, переназначение, перенос дедлайна — каждый вариант уже просчитан,
   с шансом успеть; «Варианты» сравнивают до четырёх решений бок о бок и отмечают лучшее.
4. **Согласовать.** «Сообщить» собирает из расчёта письмо заказчику и сообщения каждому затронутому исполнителю.
5. **Зафиксировать.** «Применить» пишет изменение в журнал с причиной; любое прошлое состояние можно вернуть.

### Как закрыто ТЗ
| Требование ТЗ | Где в продукте |
|---|---|
| 1. Создать проект: название, сроки, задачи, срок задачи, ответственный, статус | «Новый проект», кнопка «Задача», редактор задачи |
| 2. Связи между задачами, понимание зависимостей | Связи «окончание → начало» с паузой или нахлёстом; таймлайн, граф связей, подсветка связей при наведении |
| 3. Изменить сроки, статус, ответственного; добавить, удалить, редактировать задачу; изменить зависимости | Редактор задачи, быстрая длительность в строке таймлайна, таблица, протягивание связей в графе |
| 4. Затронутые задачи, изменение общего срока, задачи под угрозой, самые критичные, нужно ли вмешательство | Волна и панель «Что будет, если применить»: финиш было/стало, «Под угрозой», критический путь, вердикт |
| 5. Последовательность, сроки, зависимости, состояние, проблемы | Таймлайн (Гант), граф, таблица, статусная полоса, «На что обратить внимание», «Риски» |
| Демо: ≥ 8 задач, несколько связей и ответственных, выполненные и незавершённые, задача с влиянием | Демо «ФитТрек»: 13 задач, 15 связей, 6 человек, 3 выполнены, 2 в работе; «Backend +5 дн.» срывает дедлайн |
| Контр-фича | **Советник по срокам** с планом восстановления и шансом успеть у каждого варианта |

### Контр-фича: советник по срокам
- **Какую задачу решает.** ТЗ спрашивает не только «что изменится», но и «какие решения можно принять, чтобы не выйти
  за сроки». Советник отвечает на второе: перебирает приёмы управления сроками (ускорение критической задачи, нахлёст
  этапов, снятие паузы, переназначение с перегруженного человека, перенос дедлайна), прогоняет каждый через тот же
  расчёт и ранжирует: укладывается ли в дедлайн → сколько дней даёт → какой ценой.
- **План восстановления:** до 5 шагов; на каждом — самый дешёвый шаг, закрывающий отставание.
- **Надёжность:** у каждого варианта и у плана есть «шанс успеть», чтобы не выбрать решение, которое формально
  укладывается в дедлайн, но без запаса.
- **Встроен в продукт:** кнопка «Советник» / «Как вернуть сроки» в статусной полосе; выбранный вариант становится
  черновиком и показывает свою волну.
- Вокруг советника — глубина ядра: «Шанс успеть», «Шторм-тест», «Что случилось?», «Варианты», «Сообщить».

### Чем отличаемся от аналогов (обзор рынка, 2026-09-28)
| Кто | Что есть | Чего нет |
|---|---|---|
| MS Project / Planner | путь задачи, AI-статус-отчёт | песочницы what-if |
| Primavera P6, Acumen, Safran | сценарии (сравнение двух), Монте-Карло, P80 | лёгкости: экспертный enterprise |
| Jira Plans | песочница изменений | критического пути, сравнения N сценариев |
| monday, Wrike, ClickUp, Asana, Smartsheet | AI-ярлык риска | расчёта последствий, вероятностного срока |
| LiquidPlanner | Монте-Карло, ожидаемая дата | сценариев и советов |
| Битрикс24, Kaiten, YouGile, WEEEK, Яндекс Трекер | Гант, связи | what-if нет ни у кого; критического пути нет у Kaiten, YouGile, WEEEK |

Ниши, которые рынок не закрывает, а «Волна» закрывает: сравнение N сценариев бок о бок; вероятностный прогноз
в лёгком инструменте; готовый отчёт об изменении для заказчика; ранжированный список «что сорвёт проект»;
моделирование событий вместо правки полей; в российском сегменте нет ни what-if, ни Монте-Карло.

### Демо (4–5 минут, подробно — `docs/demo-script.md`)
Перед показом: меню проекта → «Сбросить демо».
1. **Проект под контролем — но насколько надёжно?** «Идёт по плану», запас 3 дня → «Шанс успеть» → «Риски»:
   вероятность, гистограмма финишей, что решает срок, шторм-тест.
2. **«Backend оказался сложнее» — главный момент.** «Что случилось?» → +5 дней → оранжевая волна по цепочке,
   дедлайн сорван на 2 дня, шанс падает, вердикт «Требуется вмешательство».
3. **Решение.** «Как вернуть сроки» → советник; сохранить вариант А; «Заказчик переносит дедлайн +1 нед.» → вариант Б;
   «Варианты» → таблица бок о бок, отмечен вариант с большим шансом.
4. **Сообщить.** Письмо заказчику и сообщения команде одной кнопкой.
5. **Отпуск сотрудника** → задачи встают на паузу, волна.
6. **Журнал и откат.** «Применить» → «Журнал» → «Вернуть как было».

Цифры шанса зависят от сегодняшней даты (прогноз учитывает прошедшие дни у задач «в работе») — сверять перед записью.

### Как устроено (для слайда)
- **Один движок на клиенте и сервере** (чистый TypeScript без зависимостей): мгновенное превью в браузере и та же
  проверка на сервере — расчёт не расходится.
- **Метод критического пути** по рабочим дням (прямой и обратный проход), флаги риска, вердикт.
- **Монте-Карло** с детерминированным генератором: одинаковые данные дают одинаковые цифры, разница до/после —
  чистый эффект изменения.
- **Черновик — список операций** (ChangeSet): превью, варианты, журнал и откат устроены одинаково; в базе только
  исходные данные, расчётное никогда не хранится.
- Стек: React 19 + Vite + Tailwind v4, Fastify 5 + zod, SQLite, встроенный в Node, собственный SVG-Гант, граф на React Flow.

## Модель данных

Хранятся только «сырые» данные. Расчётные поля (ES/EF/LS/LF, резерв, флаги, критичность)
**никогда не пишутся в БД** — их всегда считает движок.

- **Project**: id, name, description, startDate, deadline, statusDate (nullable → «сегодня» = реальная дата), createdAt
- **Person**: id, projectId, name, role, color (ответственные — справочник, не аккаунты; авторизации нет)
- **Task**: id, projectId, name, description, durationDays (int ≥ 0, 0 = веха), status, assigneeId?, dueDate? (срок выполнения), startNotEarlier? (ограничение «не раньше»), actualStart?, actualEnd?, sortOrder
- **Dependency**: id, projectId, predecessorId, successorId, lagDays, UNIQUE(predecessorId, successorId). Только Finish→Start.
  `lagDays > 0` — пауза, `lagDays < 0` — нахлёст (не больше длительности предшественника).
- **ChangeEvent**: id, projectId, createdAt, title, reason?, ops_json, snapshot_before_json, finish/buffer before/after — журнал и откат

Статусы (ручные): `not_started | in_progress | blocked | done`.
Флаги (вычисляемые, `TaskFlags`): `critical`, `lowFloat`, `missesDueDate`, `pastDeadline`, `overdue`,
`blocked`, `blockedByPredecessor`, `overloaded`. Итог по задаче — `risk: none | medium | high`
(«под угрозой» = high).

## Алгоритмы

### Календарь (`calendar.ts`)
Рабочие дни пн–пт, праздники не учитываются. Абсолютный индекс рабочего дня (0 = пн 1970-01-05).
Задача занимает полуинтервал `[es, ef)`; дата окончания = последний рабочий день. Веха — событие в конце дня
перед `es`, у неё начало = окончанию.

### Расписание (CPM, `analyze.ts`)
1. Топосортировка (Kahn, стабильная по sortOrder). Цикл → `CycleError` с конкретным циклом (DFS).
2. Прямой проход:
   - `done` с actualEnd: даты фактические, не двигаются;
   - `in_progress` с actualStart: ES = actualStart, EF = max(ES + duration, today + 1);
   - иначе: ES = max(pred.EF + lag, startNotEarlier, today (кроме done), projectStart).
     При равенстве причиной считается зависимость; `driver` запоминает, что определило ES.
3. Финиш = max(EF). Обратный проход (выполненные последователи игнорируются) → LS/LF, float = LF − EF.
   Критические = незавершённые с float ≤ 0. Критические связи: pred.EF + lag = succ.ES, обе критические.
4. Запас = endIndex(deadline) − финиш.
5. Пороги: `LOW_FLOAT_DAYS = 2`, `LOW_BUFFER_DAYS = 2`. Выравнивания ресурсов нет:
   перегруз (пересечение задач одного человека) подсвечивается, но даты не меняет.
6. Здоровье: `intervention`, если есть high-алерт; `attention`, если есть medium-алерт; иначе `ok`.

### Анализ последствий (`changeset.ts`, `impact.ts`)
- `applyChangeSet(state, ops)` — чистая функция, валидирует и проверяет цикл. Ops: `updateTask`, `createTask`,
  `deleteTask`, `addDependency`, `removeDependency`, `updateDependency`, `updateProject`.
- `applyChangeSet` также проверяет проект: непустое название, дедлайн не раньше старта.
- `mergeOps` схлопывает правки одной задачи в один патч (черновик не разрастается); при удалении задачи
  её правки и новые связи из черновика убираются, а созданная и удалённая задача исчезает целиком.
- `statusPatch` ставит фактические даты только на рабочие дни: «в работе» — старт сегодня (в выходной —
  понедельник); «выполнена» — окончание в последний рабочий день ≤ сегодня, старт плановый, если уже наступил,
  иначе отсчитывается назад на длительность задачи.
- `summarizeOps` — короткий заголовок записи журнала («… и ещё N изм.»).
- Тексты движка используют `formatShort` («7 окт») и `plural` — тот же формат, что и в UI.
- `diffAnalyses`: затронутые задачи (ΔES/ΔEF), цепочка причин по `driver` до изменённой задачи,
  Δ финиша, запас до/после, новые и снятые алерты (по `key`), изменения критического пути, заголовок, вердикт:
  `intervention` — запас < 0 или новый high-алерт; `attention` — финиш сдвинулся, новые алерты или критические задачи.
- UX: любая правка → `usePropose` (проверка движком) → черновик → расчёт на клиенте → волна + призраки
  + ImpactPanel → Применить (сервер повторно применяет тем же движком и пишет ChangeEvent) / Отменить.

### Контр-фича: советник по срокам (`advisor.ts`)
Кандидаты (каждый прогоняется через `applyChangeSet + analyze`):
ускорить критическую задачу (≤ `MAX_CRASH_SHARE` = 30%), нахлёст по критической связи (fast-tracking,
≤ `MAX_OVERLAP_SHARE` = 50% длительности предшественника), убрать паузу, снять «не раньше», переназначить
задачу перегруженного человека на свободного, перенести дедлайн (всегда последним).
Сила действия подбирается минимальной, которой хватает до дедлайна. Ранжирование: укладывается ли в дедлайн →
выигрыш → цена; если сроки в порядке — сначала то, что снимает текущие проблемы.
Жадный план: ≤ 5 шагов, на каждом — самый дешёвый шаг, закрывающий отставание, иначе самый сильный.
Советник работает по состоянию **с учётом черновика**; выбранный вариант добавляется в черновик.
У плана и каждого варианта показывается шанс успеть.

### Риски и решения (killer features, 2026-09-28)
- **«Шанс успеть»** (`forecast.ts`): 2000 прогонов `forwardPass` с длительностями из треугольного распределения
  `SPREAD` (−10% / план / +30%, подрядчик по роли «Подрядчик…» и `blocked` — до +60%); у задач в работе варьируется остаток.
  ГПСЧ детерминирован: число задачи = хэш(`sortOrder|name`) × номер прогона × seed — «общие случайные числа»
  (разница до/после = эффект изменения; пересозданное демо даёт те же цифры). `chance` = доля финишей ≤ `deadlineIndex`,
  `planChance` — ≤ детерминированного финиша, P50/P80/P95, гистограмма, `drivers` — доля прогонов, где задача на цепочке финиша.
  В UI: метрика в статусной полосе, вкладка «Риски», строка в ImpactPanel, советник, превью событий, «Варианты».
- **«Шторм-тест»** (`threats.ts`): сценарии «сложнее на 30% остатка», «человек выпадает на 5 раб. дн.» (через `compileEvent`),
  «подрядчик/ограничение: старт +5 дн.»; ранжирование: срыв дедлайна → Δфиниша → новые high-алерты, не больше двух на тип.
  `safetyMargins` = резерв + запас до дедлайна. «Проиграть» кладёт ops в черновик с причиной для журнала.
- **«Что случилось?»** (`events.ts`): `compileEvent(state, today, event, newId)` → `{ ops, title }`. Отпуск-пауза: начатая
  задача удлиняется на длину отсутствия, стартующая в отпуск получает «не раньше дня возвращения» (одного прохода
  достаточно — правки уводят задачи за окно); «передать коллеге» меняет исполнителя. Заголовок события → причина в журнале.
- **«Варианты»**: черновики хранятся в Zustand + `localStorage` (`volna:scenarios:v1:<projectId>`, ≤ 4), сравнение в
  диалоге (метрики кэшируются по массиву ops), рекомендация — максимальный шанс. Сбрасываются при «Применить» и сбросе демо.
- **«Сообщить»** (`brief.ts`): письмо заказчику по разделам (что произошло → сроки и вероятность → какое решение нужно;
  при переносе дедлайна — просьба подтвердить новый срок) и сообщения каждому затронутому исполнителю с первопричиной
  волны; копирование, `mailto:` и «Печать / PDF» (print-стили печатают только `.print-area` окна).
- В «Вариантах» строки: шанс, шкала «финиш и дедлайн», финиш, дедлайн, запас, вердикт, под угрозой, перегружены,
  что меняем; буква варианта закрепляется при сохранении, удаление — через `confirmAction`.
- Типы новых модулей (`Forecast`, `ProjectEvent`, `Threat`, `Brief`…) объявлены в `types.ts`, как и `ImpactReport`
  и типы советника. Цвета для тёмного фона — токены `--color-*-light`, тень сегментов — `--shadow-raised`,
  сегментный переключатель — `Segmented` в `ui.tsx`. Кнопка «Что случилось?» нейтральная: оранжевый — только последствия.

## Конвенции кода
- TypeScript strict, ESM, без `any` (при необходимости — `unknown` + сужение). Prettier: 2 пробела, одинарные кавычки, точки с запятой, ширина 100.
- Идентификаторы и имена файлов — на английском (camelCase / PascalCase для компонентов); тексты UI и комментарии — на русском. Комментируем только неочевидное.
- **Движок чистый**: без IO и без `new Date()` без аргументов — «сегодня» передаётся параметром. Любое изменение движка сопровождается тестом.
- **Все изменения задач и зависимостей идут только через ChangeSet** (`POST /changes`); отдельных CRUD-эндпоинтов для задач нет. Люди и сам проект (имя/описание) — обычный CRUD.
- Даты на границах (API, БД, UI) — строки `YYYY-MM-DD`. ID — `crypto.randomUUID()`.
- SQL-колонки в snake_case, маппинг — только в `repo.ts`. Вход API валидируется zod-схемами (`schemas.ts`).
- Типы домена объявляются один раз в `packages/engine/src/types.ts`.
- Frontend: серверное состояние — TanStack Query, черновик и UI — Zustand; производные данные (анализ, impact) — `useMemo` в `lib/model.ts`, не в state.
  Компоненты проекта берут модель через `useModel()`, правки отправляют через `usePropose()`.
- Дизайн-токены — в `apps/web/src/index.css` (`@theme`). Нейтральная основа: ink / ink-2 / ink-3 (текст; ink-3 —
  самый светлый, 4,9:1 на белом), paper (фон), surface, sunken (hover), pressed (active), line-soft / line / line-strong.
  Единственный акцент интерфейса — `cobalt` #1d5bd6 (кнопки primary, фокус, выделение, «в работе»).
  Цвета данных: wave (только последствия черновика; текстом — wave-deep), crimson (критично), moss (готово),
  ochre (блок; полосы — ochre-bar). Большие цветные плашки не используются — только вердикт и чипы.
  В SVG цвета берутся из токенов (`var(--color-…)`), а не хардкодом. Радиусы 6 / 8 / 12 px, тени — только у
  всплывающих слоёв (`shadow-float`). Полупрозрачности нет: утилиты `glass*` оставлены для совместимости и дают сплошной фон.
- Состояния одинаковы везде: hover — `bg-sunken`, active — `bg-pressed` (кнопки ещё `scale(.98)`), focus-visible —
  кольцо cobalt 2 px, disabled — `opacity .45` + `cursor:not-allowed`, выбранная строка — `cobalt-soft` + полоса слева.
- Всплывающие элементы: `Tooltip` — иконки без подписи и понятия (тексты из `lib/glossary.ts`, термин с подсказкой —
  `Term`, пунктир); тост внизу, 3,5 с, пауза при наведении, «Отменить» для удаления задачи и связи (возврат ops
  черновика); `Popover` — быстрые действия (длительность в строке Gantt), открывается вверх у края экрана;
  модальные окна — только необратимые действия и многошаговые диалоги. Ошибки форм — под полем (`Field error`).
- Движение: фоновые анимации есть только у логотипа (`WaveMark`) и линии волнения в статусной полосе (`SeaLine`: амплитуда и скорость = здоровье проекта, оранжевая — в режиме черновика). Остальное — 150–250 мс, ease-out, только
  `transform`/`opacity`, в ответ на действие. После пересчёта изменившиеся задачи коротко вспыхивают (`useRecalcFlash`,
  класс `.recalc-flash`); наведение/фокус на задаче выделяет её связи (Gantt и граф). `prefers-reduced-motion` отключает всё, вспышку — полностью.
- Подтверждения необратимых действий — `confirmAction()` (собственный диалог на `<dialog>`), не `window.confirm`. Для опасных действий фокус остаётся на «Отмена».
- Структура страницы проекта: верхняя панель (логотип → все проекты, название → меню проекта с параметрами и сбросом демо, вкладки с подчёркиванием (←/→ с клавиатуры; уже 1024 px — второй строкой), «Варианты N» — только если есть сохранённые, «Что случилось?», «Задача»), статусная полоса (с «Шансом успеть» → вкладка «Риски»), вид, боковая колонка. «Применить / Отменить» черновика — в закреплённой панели внизу боковой колонки (`DraftBar`) со сводкой последствий (вердикт, финиш, шанс) и «Подробнее» → полная ImpactPanel; при выбранной задаче редактор не сдвигается.
- Адаптив: от 1024 px боковая колонка рядом (360 px, с 1280 — 400 px); уже — `Sheet` (снизу на телефоне, справа на планшете), остальная страница `inert`; на телефоне DraftBar прижат к низу экрана. Вариант Tailwind `in-sheet:` прячет собственные крестики панелей внутри шторки.
- Коммиты — только по запросу пользователя.

## Запуск локально

```bash
npm install
npm run dev       # web: http://127.0.0.1:5173 (Vite проксирует /api), api: http://127.0.0.1:3001
npm start         # продакшн: собрать фронт и поднять всё на http://localhost:3001
npm test          # тесты движка (vitest)
npm run typecheck # tsc по всем пакетам
npm run seed      # пересоздать демо-проект (то же делает «Сбросить демо» в меню проекта)
npm run e2e       # сквозная проверка сценариев ТЗ через API (нужен запущенный сервер; пересоздаёт демо)
```

- БД: `apps/server/data/volna.db` (переопределяется `DB_PATH`), при пустой БД демо создаётся автоматически.
- Проект лежит в OneDrive: у Vite включён polling-watcher (`vite.config.ts`), иначе правки иногда не подхватываются.
- `npm run dev` и `npm start` используют один порт 3001 — одновременно не запускать. При занятом порте сервер
  выводит понятную подсказку; другой порт: `PORT=3002` (cmd: `set PORT=3002 && npm start`).
- Логи сервера — на английском (кириллица в JSON-логах pino искажается в консоли Windows); логи запросов
  отключены через `LogController`, чтобы не засорять терминал на демо.
- Граф (`GraphView`) грузится лениво (`React.lazy`) — отдельный чанк, основной бандл < 500 КБ.
- Превью в Claude Code: `.claude/launch.json` поднимает API (`volna-api`, 3001) и фронт (`volna-web`, 5173) отдельными
  конфигурациями — превью передаёт процессу `PORT`, и общий `npm run dev` увёл бы API на порт фронта.
  После проверки превью останавливать (`preview_stop`): иначе `npm start` / `npm run dev` упадут на занятом порте 3001.
- Gantt по умолчанию вписывает весь план в ширину (ResizeObserver, мин. 8 px на день); ручной зум отключает автоподгонку, кнопка «Вписать» возвращает её. Строка 40 px, левая колонка 280 px (на телефоне 172 px, без аватаров и карточки при наведении); метки «сегодня» и «дедлайн» — на отдельной дорожке шапки.
- Граф: узлы пересоздаются при наведении, поэтому у них явно задан `measured` — иначе React Flow сбрасывает замер и не рисует связи.
- Docker: `docker compose up --build` (или `docker build -t volna . && docker run -p 3001:3001 -v volna-data:/data volna`)
  → http://localhost:3001. Проверено 2026-09-29: образ собирается и работает на linux/amd64 и linux/arm64 (Apple Silicon,
  через эмуляцию buildx); `package-lock.json` содержит нативные бинарники rolldown/lightningcss/tailwind/esbuild для обеих
  архитектур. БД в томе `/data`, при пустой БД демо создаётся само.

  - подчёркивание вкладки — часть надписи (`span` внутри `[data-tab-label]`, `scale-x` 0/1), без JS-замеров,
    поэтому всегда ровно по ширине текста и не зависит от загрузки шрифта;
  - сводка статусов: число внутри пилюли (`StatusBadge count`); легенда в строке — только ≥ 1536 px;
  - метка срока на полосе без текста (дата — в карточке и редакторе); подпись понедельника рядом с «сегодня» скрыта;
  - `fmtRange` в `lib/format.ts`: у вехи одна дата вместо «3 ноя — 3 ноя»;
  - понятные подписи: «Готово 3 из 13», «2 задачи впереди», журнал «запас 3 дн. → запас 1 дн.»,
    «ещё 2 проблемы», «Лучший из вариантов», «Старт: в работе с 18 сен», кнопка «Варианты» с текстом (≥ 1280);
  - название задачи в редакторе — `textarea` с `field-sizing: content` (длинное видно целиком);
  - таблица: «Начало» и «Окончание» → «Даты», в «Рисках» один признак + «+N»;
  - журнал на телефоне: «Вернуть как было» под заголовком записи.
- **Логика:** при зелёном проекте советник сортирует `rankCalm` (снимает проблемы → без побочных эффектов →
  дешевле → сильнее); «Отпуск» по умолчанию предлагает человека с работой в эти дни; превью растягивания задачи
  «в работе» не короче «сегодня + 1» (как движок); короткое сообщение «Сообщить» содержит выбранное решение;
  подпись React Flow больше не скрыта (`attributionPosition="top-right"`).
- **История черновика** (`history` в `store/draft.ts`, до 50 шагов): Ctrl+Z (`DraftUndoHotkey` в `ProjectPage`)
  возвращает черновик на шаг назад; `solution` — выбранное в советнике решение для письма.

## Как снова поднять сайт (Render + cron-job.org)
1. **Сервис жив, нужен новый код:** dashboard.render.com → volna → **Manual Deploy → Deploy latest commit**
   (Auto-Deploy выключен). Сборка 5–8 мин.
2. **Сервис приостановлен (Suspend):** volna → **Resume Service**; адрес тот же.
3. **Сервис удалён:** Render → New → **Blueprint** → репозиторий `bodhiswaga/Hackathon-Volna`, ветка `main`
   (Blueprint Path пустой — `render.yaml` в корне) → Apply. Адрес будет новым — обновить README и QR.
4. **Пингер:** cron-job.org → Create cronjob → URL `https://<адрес>/api/health`, каждые 10 минут, Enable job.
   Без него бесплатный сервис засыпает через 15 мин, первое открытие — до минуты.
5. **Проверка:** `https://<адрес>/api/health` → `{"ok":true}`; главная открывается; перед показом —
   меню проекта → «Сбросить демо». База эфемерная: после рестарта демо создаётся заново само.

## Допущения, которые могут быть пересмотрены
Даты вычисляются из длительности (мышью на Gantt не тянутся) · нет праздников РФ · «сегодня» сдвигает
незавершённые задачи · нет выравнивания ресурсов · `blocked` — флаг + «не раньше сегодня» ·
пороги (float ≤ 2, ускорение ≤ 30%, нахлёст ≤ 50%) условные · советник эвристический · node:sqlite вместо Prisma ·
без авторизации · срыв промежуточного срока задачи — high-алерт даже при соблюдении дедлайна.
