# Сценарий демонстрации «Волны» (3–4 минуты)

**Перед показом:** запустить `npm start` (или `npm run dev`), открыть http://localhost:3001 (для dev — :5173),
открыть демо-проект и нажать **«Сбросить демо»** в правом верхнем углу. Даты демо считаются от сегодняшнего дня,
поэтому картина каждый раз одна и та же: часть работ выполнена, часть в работе, запас до дедлайна 3 рабочих дня.

Демо-проект «Запуск мобильного приложения „ФитТрек“»: 13 задач, 6 участников (включая подрядчика),
15 зависимостей. Три задачи выполнены, две в работе, остальные впереди.

---

## 1. Проект под контролем (30 сек)

- Статусная полоса сверху: **«Идёт по плану»**, прогноз финиша, дедлайн, запас 3 дня, 6 задач на критическом пути.
- **Таймлайн:** выполненные задачи зелёные, текущие синие. Красная обводка — критический путь,
  пунктирный хвост — резерв задачи. Синяя линия — сегодня, красный пунктир — дедлайн, флажки — сроки задач.
- Справа — критический путь списком: «Задержка любой из этих задач сдвигает финиш».

> Мысль для жюри: руководитель за 5 секунд видит, где проект уязвим.

## 2. «Backend оказался сложнее» (60 сек) — главный момент

- Кликнуть задачу **«Backend: API, база данных, авторизация»** → в блоке «Что если…» нажать **+5 дн.**
- Показать **волну**: оранжевые полосы расходятся по цепочке, серые «призраки» показывают прежние даты,
  у каждой задачи бейдж сдвига.
- Панель **«Что будет, если применить»**:
  - вердикт **«Требуется вмешательство»**;
  - финиш сдвигается на +5 рабочих дней, проект **выходит за дедлайн на 2 дня**;
  - сдвигаются 5 зависимых задач, у каждой видна причина и цепочка
    («Backend → Интеграция → Тестирование → …»);
  - «На что обратить внимание»: какие задачи не успевают к своим срокам.
- Подчеркнуть: **план ещё не изменён** — это черновик, его можно отменить.

> Ответ на главный вопрос кейса: «что произойдёт с проектом и на что обратить внимание».

## 3. Советник: как вернуть сроки (45 сек) — контр-фича

- Нажать **«Подобрать решение»** (или оранжевую кнопку «Как вернуть сроки»).
- Советник уже просчитал каждый вариант тем же движком:
  - **Ускорить Backend на 2 дня** (добавить разработчика) → укладываемся;
  - **Начать интеграцию раньше** — частичное распараллеливание, цена высокая: риск доработок;
  - точечные ускорения других задач;
  - честный запасной вариант — **перенос дедлайна**.
- **План восстановления** — минимальный набор шагов, чтобы уложиться в дедлайн.
- Нажать **«Попробовать план»** → черновик пересчитан: финиш снова в дедлайне.
  При этом промежуточные сроки двух задач всё ещё срываются, и система честно об этом говорит.
- Ввести причину («Backend сложнее оценки, добавили второго разработчика») → **«Применить изменения»**.

## 4. Сотрудник уходит в отпуск (30 сек)

- Кликнуть **«Маркетинговые материалы для сторов»** (Игорь) → «Ответственный недоступен» → передать **Марии**.
- Вердикт: «Есть последствия». Срок не меняется, но **Мария перегружена**: две задачи одновременно.
- Открыть **Советник** → первым идёт «Передать задачу → Анна Смирнова» (у неё окно свободно) → «Попробовать».
- Отменить черновик (или применить).

## 5. Журнал и откат (20 сек)

- Вкладка **«Журнал»**: каждое изменение с причиной и эффектом («финиш 30 окт → 4 нояб, +3 дн.»).
- **«Вернуть как было»** — план откатывается, откат тоже попадает в журнал.

## 6. Другие представления (15 сек, если есть время)

- **Граф связей** — зависимости и критический путь. Связь можно протянуть мышью, и она сразу проверяется
  на цикл: попробуйте замкнуть «Релиз → Анализ требований», система покажет ошибку.
- **Задачи** — таблица с быстрым редактированием статусов, ответственных и длительности.
- **Команда** — загрузка людей, перегрузки подсвечены.

## Как это устроено (если спросят)

- **Критический путь:** метод CPM. Топологическая сортировка по Кану, прямой и обратный проходы по рабочим дням,
  резерв = поздний финиш − ранний финиш. Выполненные задачи зафиксированы по фактическим датам,
  незавершённые не планируются в прошлом.
- **Волна:** движок хранит для каждой задачи «ведущего предшественника» — того, кто определил её старт.
  По этим ссылкам строится цепочка причин.
- **What-if:** один и тот же TypeScript-движок работает в браузере (мгновенный предпросмотр)
  и на сервере (повторная проверка при применении).
- **Советник:** генерирует варианты (ускорение ≤ 30% длительности, нахлёст ≤ 50% предшественника,
  снятие пауз и ограничений, переназначение, перенос дедлайна), прогоняет каждый через движок
  и выбирает минимальное воздействие, которого хватает до дедлайна.
